# Operating a cluster, compared with a classic stack

**The question:** What did an operator have to do to run the scoreboard on the
Atanor container cluster, and how does that compare with an app server,
Postgres, a queue and Redis behind the same balancer?

This page stands alone. It is an assessment, not a benchmark. Read it with these
limits in mind:

- **Observed** means it was done or measured in this repository, on one machine
  (12 cores, Docker). The sources are named.
- **Inference** means it comes from common practice with the classic stack. Nothing
  of the classic stack was built or measured here.
- The scoreboard is a small app (see [examples/scoreboard](../examples/scoreboard/README.md)):
  rooms with writes and rankings, a job that ranks, and a WebSocket per room. A
  real application has more of everything on both sides.

## What the operator did on Atanor (observed)

The steps are in [how-to-run-a-cluster-in-containers.md](how-to-run-a-cluster-in-containers.md).

files replicated to the store), jobs, alarms and WebSocket push are part of the node.

### What the chaos runs showed (observed)

From step 7 of the how-to, 15 runs of 3 nodes at 60 requests per second, about
59,000 acknowledged writes in the first 12:

- No acknowledged write was lost or duplicated.
- A killed node's cells were served again by another node in 0.9 to 7.5 s, a
  partitioned node's in 13.2 and 13.3 s, a paused node's in 18.8 and 19.4 s, and
  the store's restart in 32 and 34 s (8.1 s in a later run).
- `rollout-deploy` was atomic for clients: the last answer from the old version
  came 17 ms before the first from the new one, in both runs, and nothing was refused.
- `rollout-restart` (a new image, one node at a time) refused 42 and 51
  requests of about 4,700 before a cell call of a handler learned to wait for a leaving owner, none stored. After it, two runs refused 0.
- The balancer left a partitioned node out of rotation within about two seconds
  once it asked `/health/serving`; with `/health/ready` it sent
  that node a third of the traffic.

## Classic stack (inference from common practice, not measured here)

An app server (Phoenix or Node), Postgres, a queue (a jobs table or RabbitMQ) and
Redis, behind HAProxy. To get the same behavior, an operator typically has to:

- run Postgres with a replica and a failover mechanism (Patroni, a managed service,
  or a runbook), and decide what happens to writes while it promotes;
- put a connection pooler (PgBouncer or the app's pool) between N app servers and
  Postgres, and size it;
- run migrations at each deploy, in an order that old and new code both tolerate;
- schedule backups and test a restore;
- run queue workers (a separate process type, or Oban/BullMQ in the app), with
  retries, a dead-letter set and idempotent handlers;
- run Redis for presence and broadcast between app servers (or Postgres
  `LISTEN/NOTIFY`), and decide on its own persistence and failover;
- for WebSockets, either sticky sessions at the balancer or a pub/sub fan-out;
- deploy the app server by rolling restarts with a drain period;
- monitor each of Postgres, the queue, Redis and the app.

That is four stateful or stateless server kinds besides the balancer, plus the
database, the queue and the cache each with its own configuration and secrets.
The count is typical, not a requirement: a managed database and a managed Redis move
work to a vendor but do not remove the items.

## Simpler on Atanor

1. **One kind of stateful server to run.** State is SQLite per cell, replicated to an
   S3 store; the node holds no data that the store lacks. Observed: 5 containers
   for everything, compared with a database, a replica, a queue and Redis in the
   classic list (inference).
2. **No database failover runbook.** A cell has one owner at a time, held by a lease in
   the store; when a node dies another takes the cell over. Observed: kill, pause and
   partition runs lost nothing, and the operator ran no command to promote anything
   (step 7; [how-to-run-a-cluster.md](how-to-run-a-cluster.md)).
3. **No separate queue to drain.** Jobs are rows in the cell's SQLite and run on the
   cell owner with retries and a dead-letter set ([design §15](design.md#15-jobs-per-cell-and-bulk-operations)).
   A rollout leaves nothing in a queue to finish first.
4. **No Redis, no sticky sessions.** WebSockets attach to cells and push from the owner
   on any node ([how-to-use-websockets.md](how-to-use-websockets.md),
   [ephemeral messages](how-to-share-ephemeral-messages.md)). Observed: the WebSocket
   client of the chaos runs missed 0 to 3 acknowledged writes while reconnecting in
   14 of 15 runs, and 140 in one `pause` run.
5. **No connection pool to size.** There is no database connection per request.
   Observed: 9 to 19 store connections in use, constant, during the load of the stall check.
6. **Worker deploys are one command and atomic.** `atanor deploy --activate` with a token
   limited to one worker; migrations travel in the package
   ([how-to-deploy-a-worker.md](how-to-deploy-a-worker.md)). Observed: `rollout-deploy`
   switched all rooms in 17 ms with nothing refused. A rehearsal can apply the
   migrations to copies first ([how-to-run-a-migration-rehearsal.md](how-to-run-a-migration-rehearsal.md)).
7. **Node rollouts are tested under load.** Observed: `rollout-restart` with 0 refusals
   in two runs after that change.
8. **Few moving parts for the mesh.** Nodes find each other through the bucket
   ([discovery](configuration.md#discovery)), with no list of peers, and keep their name when a
   container restarts with another address. Observed: no manual step.

## Harder on Atanor

1. **The Erlang cookie is a root password.** Anyone who has it and can reach the
   distribution port can run code on every node. The cluster mounts it as a secret
   and publishes only the balancer's ports, on loopback. The classic stack has no equivalent
   single shared secret (inference). See [design §4](design.md#4-bindings), "What the cookie protects".
2. **Rules for feed grouping.** Grouped feed objects are on by default.
   A reader of the change feed outside the instance must use the same
   Alambique as the nodes, and `linger_ms` must be at most a tenth of `window_ms`,
   or the instance refuses to start ([configuration.md](configuration.md)).
3. **A WASM toolchain for the app.** The scoreboard is Rust built to `wasm32-wasip2`
   (`scripts/build-scoreboard`, 339 lines of guest code plus a WIT world), not
   Elixir or Node ([how-to-write-a-wasm-worker.md](how-to-write-a-wasm-worker.md)). A
   native Elixir worker avoids it but runs in the node's image.
4. **A cell comes back about 19 s after a pause.** Observed: 18.8 and 19.4 s for a
   frozen node, 13 s for a partition, from the detector's decision, not the 30 s lease
   ([the design](design.md#810-acting-on-a-confirmed-failure)).
   A failover that promotes a replica takes seconds to a minute in the classic stack
   (inference); the difference is not measured.
5. **A store restart pauses all writes for about 30 s.** Observed: cells were served
   again 32 and 34 s after the restart began. The store is one SeaweedFS process here,
   not a replicated bucket ([the README](../README.md#limitations)).
6. **The client must handle two kinds of failed answer.** A refused call (503 `unavailable`,
   including `fenced`) did not run; 503 `unknown_outcome` may have run and is not repeated by Atanor
   ([the design](design.md#84-when-the-node-is-lost)).
   With Alambique's current behavior a write is `fenced` only when it did not run.
   The scoreboard needs ids on writes (`once=1`) to be safe to retry. Observed: all
   12 unknown writes of the `pause` run 1 were stored.
7. **Effects outside the cell can happen twice around a takeover.** A handler that
   started before a takeover runs to the end ([the design](design.md#813-a-handler-that-outlives-its-cell)).
8. **A cell may run the old schema for seconds after a deploy.** Migrations must be
   additive ([the design](design.md#41-cells-and-schemas)).
9. **WASM workers pay a network hop per cell call.** They do not run on the owner
   ([the design](design.md#814-ingress-and-owner-what-runs-where)).
10. **The operator builds the image.** The cluster here builds it
    with Alambique fetched at the pinned release, with Rust for both NIFs.
11. **The audit log has no retention**, and a deploy token is still the
    authority of its manifest for some grants
    ([audit log](design.md#102-admin-api),
    [grants](design.md#33-what-a-manifest-may-grant)).

## Missing in Atanor

1. **The stalls came from the host's btrfs.** Above about 60
   requests per second the container cluster stalled for about 2 s every 6 to 10 s when its
   data was on btrfs. With the data of the store and the nodes on tmpfs
   (`ATANOR_CLUSTER_TMPFS=1`) it ran 200 requests per second without stalls
   ([how-to-run-a-cluster-in-containers.md](how-to-run-a-cluster-in-containers.md#keeping-the-data-in-memory)).
   It is a limit of the host's file system, not of Atanor or Alambique. Latency figures taken on btrfs
   in this page and in the chaos table include those stalls.
2. **Unknown outcomes are named.** A write whose batch was sent
   when its cell stopped is answered `unknown_outcome`, never `fenced`: 0 refused writes
   were stored in 2 `store-restart` runs with the current Alambique, where one `fenced` write had been
   stored before. A stopped router answers
   `draining`; Atanor still maps three shapes of a stopped instance to `owner_down`,
   and others would surface as 500.
3. **Quorum-aware health is new.** `GET /health/serving` reports whether the node is in the majority;
   without it the balancer kept sending a third of the traffic to a cut-off node.
   It has been run in the container cluster only.
4. **Seeing which node owns a cell takes an admin call.** `GET /cells?node=` lists
   the cells of one node, and the chaos script asks it for every room
   ([how-to-use-the-admin-api.md](how-to-use-the-admin-api.md)). The dashboard lists
   live cells; its charts start when the page is opened ([how-to-open-the-dashboard.md](how-to-open-the-dashboard.md)).
   There is no single "who owns room X" command; this is an inference from the
   documented endpoints.
5. **Store backups and restore are the operator's.** Cells live in the bucket. Atanor
   documents no backup of it, and no recovery from the loss of the bucket. Alambique
   can rewind a cell to a recorded position ([design §15](design.md#15-jobs-per-cell-and-bulk-operations)),
   which is not a backup. A crash report does not survive a machine that never
   returns ([the design](design.md#172-crash-diagnostics)).
6. **Observability is telemetry events and a dashboard, not a stack.** There is
   [telemetry.md](telemetry.md), an admin API and a read-only dashboard
   ([design §10](design.md#10-observability)). The documentation describes no metrics exporter, alert rules or log
   shipping; the chaos runs sampled stacks by hand to find the btrfs stalls.
7. **No autoscaling.** The cluster here has 1 to 10 nodes set at start
   (`ATANOR_CLUSTER_NODES`). Hot cells can move to a less loaded node
   ([how-to-place-hot-cells.md](how-to-place-hot-cells.md)); adding nodes is the
   operator's.
8. **Not measured beyond one machine.** All numbers come from 12 cores, one Docker host,
   one SeaweedFS process; a real network, a replicated bucket, long runs and more than 3
   nodes were not tried ([the README](../README.md#limitations)).

## Reading the result

On the operator's day-to-day, Atanor removed the database failover, the queue and
Redis from what the operator runs, and the two commands plus 324 lines of
infrastructure files are observed facts. Whether that is a net gain depends on two
items that the classic stack does not have in the same form: the `fenced` outcome, and a client that must tell
refused from unknown. Fix those, or accept them, before comparing latency or throughput; take latency figures with
the data on tmpfs or on a file system that does not stall.
